# Description 调优与负样本设计

## 第一原则：description **只写触发条件，不写工作流**

```yaml
# ❌ 错误：description 里描述工作流程
description: |
  先读取用户输入，调用 <cli> export create，
  再轮询 status，最后调用 download 生成下载链接...

# ✅ 正确：只写"何时来找我"
description: |
  当用户需要通过 示例业务平台对媒资数据进行
  导出、清洗、巡检等操作时触发
```

**原理**：description 里写工作流，等于把决策权从 Agent 手里抢走了——但 Agent 比你更了解当前上下文，它自己能决定调用顺序。**你只需要告诉它「什么时候来找我」，不需要告诉它「来了以后一步步怎么走」**。

工作流应该放在 `<EXTREMELY-IMPORTANT>` 铁律 + `references/operations-guide.md` 里，不要塞 description。

## 第二原则：触发词中英文混合最佳

| 元素 | 策略 |
|------|------|
| 主体描述 | 用中文，贴合用户沟通习惯 |
| 功能模块名 | 保留英文命令词（`export` / `clean` / `inspect` / `compare` / `dashboard`） |
| 触发示例 | 用中文口语（「帮我导出这批数据」「查一下任务跑完了没」） |

中英文混合的好处：

- 中文匹配用户**自然语言**输入
- 英文匹配用户**直呼 CLI 子命令**输入
- 双语关键词覆盖 → 触发率高

## 第三原则：先确定触发阈值，再写触发词

不同类型 skill 的触发策略不同：

| Skill 类型 | 推荐策略 | 原因 |
|-----|------|------|
| 自有业务操作入口（example-cli、内部 CLI、团队平台） | **1% 命中原则：可能相关就先触发，再在 skill 内澄清/退出** | 漏触发会让 Agent 去 WebSearch、SQL、BI 等错误工具；触发后可通过项目/字段查询或追问收敛 |
| 通用能力 / 外部工具 / 容易污染上下文的泛技能 | 精准触发，负样本严格 | 误触发会污染上下文，且通常没有业务内澄清机制 |

### 1% 命中原则（自有业务入口）

当 skill 是团队自有平台的操作入口时，description 和顶部铁律应明确：

```markdown
只要用户请求出现本业务子模块词（如导出、清洗、数据看板、巡检、对账、字段、上传、任务状态），并且对象可能是数据、媒资、项目、字段、文件、任务或看板，即使只有 1% 可能相关，也先触发本 skill；信息不足时在 skill 内查询/追问，最终确认不是本业务时再退出。
```

真实失败案例：

```text
用户：「导出迪丽热巴主演的电视剧」
Agent 判断：这是查询公开影视资料 → 改用 WebSearch
根因：description 只写了 example-cli / <cli> / 项目字段，没有覆盖“演员/主演 + 导出 + 电视剧”的自然语言业务条件，也没有声明“导出类请求先触发 skill”。
修复：在 description 中加入演员/主演/导演/明星/艺人/剧名/片名等业务触发词，并在铁律中写 1% 命中原则。
```

### 精准触发原则（通用技能）

| 案例 | 评估 |
|-----|------|
| ❌「运营数据看板」 | 太宽泛，任何涉及"看板"的请求都可能误触发 |
| ✅「媒资多图文运营日报」 | 精确到具体业务场景 |
| ❌「数据相关任务」 | 任何含"数据"的请求都触发，污染严重 |
| ✅「腾讯视频媒资库 saas_tencentvideo_* 项目数据治理（导出/清洗/巡检）」 | 把项目前缀都写出来，触发条件极精准 |

**原则**：不是所有 skill 都该宽触发。自有业务入口要降低漏触发；通用技能要控制误触发。

## 第四原则：负样本设计——近似案例 > 明显无关

最有价值的 negative cases **不是**「帮我订一杯咖啡」这种明显无关的，而是**近似案例**——容易误触发但其实不该触发的：

| 近似 Case | 为什么有价值 |
|----------|------------|
| 「用 pandas 把空值填充一下，去掉重复行」 | 有"数据清洗"字样，但是本地脚本，不走 example-cli |
| 「示例业务平台变慢，p99 延迟涨到 8s，帮我查 file trace」 | 有 example-cli 字样，但走性能排障，应触发 file-trace Skill |
| 「帮我写 Python 脚本直连 MySQL 导出数据」 | 有"导出"意图，但不走 <cli> CLI |
| 「在腾讯云控制台创建 COS bucket」 | 有 COS 关键词，但是控制台操作 |

这类 case 能精准测出 description 是否存在「关键词误触发」问题。

### 负样本怎么写进 description

example-cli 实战写法：

```yaml
description: |
  ...（正向触发关键词、业务场景、口语化例句）...

  不要触发：与媒资业务数据无关的通用 SQL 查询；
  project create/update/import-mysql（运维向，本技能不展开）。
```

负样本段落要：

- 用「不要触发」/「不适用」/「以下场景不要触发」作为段首关键词
- 给出具体场景，不要写"其它情况不触发"这种空话
- 含歧义的近似 case 必须明确点名

## 第五原则：description 里要写「需要的前置条件」

让 Agent **加载 skill 时就知道有哪些前置依赖**——不要等用户问到一半才发现 token 没配。

example-cli 实战：

```yaml
description: |
  ...
  前置：<cli> CLI 二进制与本 SKILL.md 同目录；
  执行任何子命令前先 `source find_cli.sh`（脚本会自动从
  ~/.zshrc 等抠出 API token 并 export 到本 shell）。
```

前置条件包括（按需选用）：

- 必需的 CLI 二进制 / 工具
- 必需的环境变量 / token
- 必需的网络可达性（如private gateway）
- 必需的权限申请

## 终版 description 模板（可直接套用）

````yaml
description: |
  <平台/工具名>（CLI：<cli-name>）操作技能。覆盖<业务领域>——
  <对象 1>、<对象 2>、<对象 3>等的<动作 1>、<动作 2>、<动作 3>。

  当用户用中文描述以下需求时唤醒（未必出现 <平台名>/<CLI> 字样）：
  - <场景 1>，例如「<口语化例句 1>」「<口语化例句 2>」
  - <场景 2>，例如「<口语化例句 3>」
  - <场景 3>，例如「<口语化例句 4>」

  也覆盖直呼 CLI 子命令：<cmd1>、<cmd2>、<cmd3>。

  关键词：<平台名>、<cli-name>、<业务术语 1>、<业务术语 2>。

  不要触发：
  - <近似但不该触发的场景 1>
  - <近似但不该触发的场景 2>
  - <运维/管理向不展开的子命令>

  前置：
  - <CLI 二进制位置说明>
  - <token / 凭证要求>
  - <其它环境依赖>
````

## review 时的 description 三连查

```bash
SKILL=skills/<your-skill>/SKILL.md

# 1. description 里有没有写工作流（动词如"先调用""然后""最后"）
awk '/^description:/,/^---|^[a-z]+:/' "$SKILL" | grep -E "(先|然后|最后|首先|接着|再|调用|invoke|加载)"

# 2. 有没有「不要触发」/「不适用」段落
awk '/^description:/,/^---|^[a-z]+:/' "$SKILL" | grep -E "(不要触发|不适用|以下场景不要)"

# 3. 触发关键词是否过宽（"数据"、"任务"等单字关键词出现次数）
awk '/^description:/,/^---|^[a-z]+:/' "$SKILL" | grep -oE '数据|任务|平台|工具' | sort | uniq -c
```

判断：

- 第 1 条**有命中** → 必改（description 里不该写工作流）
- 第 2 条**没命中** → 必改（缺少负样本）
- 第 3 条**计数 > 5** → 警告（触发词可能过宽）
